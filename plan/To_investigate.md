# To investigate

- [ ] **LLM-as-judge evaluation pipeline** (part of [#37](https://github.com/garyseconomics/chatbot/issues/37)) -- Run each test question against multiple (prompt × model) combinations and use an LLM judge to evaluate whether the answer meets the expected behavior criteria. This gives a systematic way to compare prompt versions and model backends. Tasks: (1) define evaluation dataset format and create initial entries from known issues; (2) build the eval pipeline to run questions against combinations; (3) implement LLM-as-judge scoring against expected behavior criteria; (4) store results in a database/file for comparison across runs; (5) re-run the eval pipeline after each prompt change to check for regressions.
- [ ] **Query expansion for economics terms** -- Add an intermediate step before the vector search that expands economics questions with related terms. For example, "What is Gary's view on MMT?" could also search for "money printing", "quantitative easing", "government spending", "fiat currency". Currently the vector search for MMT returns irrelevant results even though Gary has discussed related concepts (money printing in "How COVID-19 Makes the Rich Richer", QE in "MOOC Part 4"). Not necessary yet — the bot handles MMT questions well enough without it — but worth keeping in mind as we add more content and encounter more cases where users use technical terms for concepts Gary explains in plain language.
- [ ] **DSPy** -- Framework for programming (not prompting) language models. Explore for
  prompt optimization and evaluation. See `prompt_experiments.py` for initial experiments.
- [ ] **MLflow** -- Platform for tracking ML experiments, models, and metrics. Explore for
  tracking prompt experiments and RAG pipeline performance.
- [ ] **OpenBrain (OB1)** -- Framework for adding memory to AI agents. No longer relevant for multi-turn conversations: per #68 (data privacy), conversation memory in production will be short-lived/in-session only (not persisted), so a persistent-memory framework doesn't fit that use case. Possibly useful instead as a **knowledge management system for the MCP server**, once it has growing, varied knowledge sources beyond video transcripts (Piketty/Zucman docs, etc.) — worth exploring in that context. [Getting started docs](https://github.com/NateBJones-Projects/OB1/blob/main/docs/01-getting-started.md).
- [ ] **Intent classification and query routing** -- The bot currently sends every question through the same pipeline (vector search → prompt → LLM). Many prompt issues (RAG internals leaking, off-topic answers, identity confusion) come from this one-size-fits-all approach. Investigated three options for routing queries to different strategies:
  - **Option A: Keyword/regex pre-processing** — Detect known patterns (meta-questions about the bot, greetings, troll signals) before the LLM call. Pros: zero cost, fast, predictable. Cons: can't catch subtle cases like off-topic questions wrapped in economics framing ("Which Pink Floyd song is the best metaphor for economics?").
  - **Option B: Local LLM classification** — Use the local Ollama fallback model to classify intent before the main pipeline. Pros: free (hardware already exists), can handle subtle cases. Cons: adds latency (local model is slow, 3-14s), cold starts up to 60s, adds complexity.
  - **Option C: Cloud LLM classification** — Use the same cloud provider to classify before answering. Pros: fast, handles subtle cases. Cons: doubles the API cost per query — problematic at scale (3,000 Patreon users → 1M+ YouTube subscribers), and this project has no revenue.
  - **Recommended approach:** Start with Option A (keyword checks) for the obvious patterns — this is free, fast, and covers most cases from the Phase 1 prompt issues. Add LLM classification later only if keyword checks prove insufficient. The LangGraph framework already in use supports conditional routing natively.
- [ ] **Research: patterns from OpenClaw** -- Studied [OpenClaw](https://github.com/openclaw/openclaw.git) for patterns applicable to this bot (2026-04-02). Summary of what's still relevant:
  - **Message chunking (#33 — already resolved for us):** OpenClaw splits responses into multiple messages after generation, rather than asking the LLM for a shorter answer — preferring paragraph/word boundaries and handling markdown code fences specially so a split never breaks a fenced block. Our sentence-chunker (merged via #51) follows the same "split after generation" philosophy, so this is historical confirmation rather than new direction.
  - **Conversation memory (#6):** OpenClaw uses two tiers — short-term in-memory history (default 50 messages per session, LRU eviction once 1000 sessions are tracked) and long-term disk-based memory triggered by a "memory flush" before the context window fills, searchable later via hybrid vector+text search. For this bot, short-term history is the priority (see #6's proposed 3-exchange window); the memory-flush pattern (the LLM itself decides what's worth remembering long-term) is a more advanced option worth considering later, not now.
  - **Intent classification and routing:** OpenClaw doesn't classify intent at all — it routes by who's asking and which channel/peer, with each route pointing to a differently-configured agent. This doesn't map onto Gary's bot (one agent, not several routed agents), so it doesn't change the recommendation already given in the "Intent classification and query routing" item above.
  - **RAG integration — tool-based vs. always-run:** OpenClaw exposes RAG as a tool the LLM decides whether to call, instead of always running it on every message. This is the direction the MCP server move (#65) points toward — worth revisiting once MCP tool-based RAG exists, rather than the current always-run pipeline. Also relevant to #69 (video link suggestions as an MCP tool), which is the same "let the LLM/server decide via a tool" shape.

  Related: #33 (long messages, resolved), #6 (multi-turn conversations), #65 (MCP server), #69 (video link suggestions), and the intent classification item above.
